# anime-prompt-forge：动漫出图提示词合成器

给 AI Agent 用的出图提示词引擎。用户不用理解「检索 / 组合 / 编码」这些概念，
你负责按四步问清需求，然后调脚本出成品。

## 核心认知：画风和题材必须分开问

这个库最重要的一条结构约束，四步不是随便分的：

| 步骤 | 决定 | 不给它会怎样 |
|---|---|---|
| **画风** style | 怎么画（笔触、上色、材质） | 模型按题材自己挑默认画法，同一题材连出十张差别很大 |
| **题材** theme | 画什么（场景、人物、情境） | 画风与版式没有承载对象，只能画成一张泛用插画 |
| **版式** layout | 怎么摆（元素分布） | 画面居中平铺，社媒图与信息图基本不可用 |
| **配色** palette | 什么色（主色 + 点缀） | 颜色偶然决定，整幅不会有统一色调 |

**不要把画风和题材混在一句话里问。** 用户说"我想要赛璐璐风格的校园少女"，
这是两件事：`--style ST-001 --theme TH-020`。混着给会两边都不到位。

**四步都齐了出图最稳。** 缺步时脚本仍会输出，但会逐条告诉你缺哪一层、缺了会怎样——
把那几条也念给用户听，不要只给一段看着完整的提示词。

## 怎么用

所有能力都在 `scripts/forge.js`，一条命令一件事。

### 0. 先判断该走哪条路

| 用户的状态 | 走哪条 |
|---|---|
| 「我想要校园少女、赛璐璐风格」——**说得出要什么** | `build`（第 2 节） |
| 「随便给我看点东西」／「不知道画什么」——**说不出要什么** | `draw`（第 3 节） |
| 只是想知道库里有什么 | `list`（第 1 节） |
| 想要一张真图，不只是提示词 | `render`（第 4 节），或 `draw --render` |

不要对着「不知道要什么」的用户硬问四步。那种情况下问题本身没意义，
直接 `draw` 铺一组出来让他挑，比来回问五轮快得多。

### 1. 不知道选什么 → 先列候选

```bash
node scripts/forge.js list style
node scripts/forge.js list theme
node scripts/forge.js list layout      # 带建议画幅
node scripts/forge.js list palette     # 带主色 HEX
```

按关键词筛：`node scripts/forge.js list style --grep 水墨`

输出第一列是**规范码**（`ST-001` / `TH-020` / `LT-001` / `PL-001`），
拿去喂 build 命令。旧 ID（`A1-01` / `G-20`）也认，但优先用规范码。

### 2. 出提示词

```bash
node scripts/forge.js build \
  --style ST-001 --theme TH-020 --layout LT-001 --palette PL-001
```

输出五段：中文正文 / 英文正文 / 标签速用版 / 负面词 / 建议画幅 / 授权 / 组合明细。

加 `--lang zh` 或 `--lang en` 只出单语；加 `--json` 走程序化处理。

### 3. 用户没想好 → 直接抽一组

```bash
node scripts/forge.js draw --n 4                       # 抽 4 组
node scripts/forge.js draw --n 4 --lock style=ST-001   # 画风固定，其余随机
node scripts/forge.js draw --n 4 --seed 7              # 可复现
node scripts/forge.js draw --n 4 --prompt              # 连中英正文一起给
node scripts/forge.js draw --n 4 --json                # 程序化取
```

每组输出一行组合信息：`层名 · 编码 · 中文名`，外加一行可复制的组合串。
**把这几行原样给用户看**，让他说「要第 2 个」——那比念四段正文让他选有效得多。

两个要点：

- **`--lock` 可以给多次**，用来固定某一层：
  `--lock style=ST-001 --lock theme=TH-020`。值可以是规范码，也可以是旧 ID。
- **抽到的组合喂给 build** 就是精修路径：
  `draw` 给出组合串 → 用户挑一组 → `build --style … --theme …` 出完整正文。

`draw` 与网页端「一键抽卡」是**同一套引擎**（`scripts/gacha-core.js`，
与仓库的 `assets/gacha.js` 逐字相同的副本），
所以槽位、锁定语义、去重规则、组合空间都一致 —— 不用两边各学一遍。

### 3.5 按模型优化提示词（先做这一步，再谈出图）

**五个模型的提示词语法不同，不能互相替代。** 这一条是本技能最容易被忽略、
也最影响结果的地方：

| 模型 | 它吃什么 | 不能给什么 |
|---|---|---|
| GPT-Image 2 | 自然语言段落、指令句 | 逗号标签流 |
| Nano Banana 2.1 | 长指令、显式 Avoid | 挤成一整段的描述 |
| Midjourney | **只吃逗号标签 + `--` 参数** | 整段正文（会被当成乱码词流） |
| Flux | T5 吃长描述性散文 | 权重语法 `(词:1.2)`（不解析，会变成画面里的字面符号）、`masterpiece` 这类质量词 |
| Sana | 自然语言，**中段长度** | 过长的后半段（会弱化前面的主体） |

所以只要用户说了具体模型，就用 `--model`：

```bash
node scripts/forge.js build --style ST-001 --theme TH-020 --model flux
node scripts/forge.js build --style ST-001 --theme TH-020 --model mj --json
```

- 文本输出会在通用正文之后**追加一段该模型的优化版**，并先说明「这版改了什么」。
  两段都给是有意的：只给优化版的话，读者无从判断它是不是少了什么约束。
- `--json` 时多四个字段：`model` / `modelPrompt` / `modelParams` / `modelNote`。
  `en` 仍然是通用正文（基准），`modelPrompt` 是优化版 —— **不互相覆盖**。

**输出永远带 `explain`（效果说明）。** 回答「这张图会怎么变」：
四步各自决定什么（`changed[].role`）、恒定保留什么（`keepAlways`，禁项每版自带）、
所选画风在五个模型上的激活标定（`styleFit`，改写层已按它调整写法）、
测试状态与限制（`limits`，read 不是 test）。向用户转述结果时**必须带上这段**，
不能只甩一大段英文正文——用户需要知道系统替他做了什么决定、哪些话没经过实测。

**MJ 的标签与参数分开给。** 它要求标签里混进 `--ar` 之外的符号就废，
所以 `modelPrompt` 是纯标签，`modelParams` 是 `--ar 1:1 --niji 6 --stylize 150`，
粘的时候标签在前、参数在后连成一段。

**MJ 那一项不能出图**（没有公开 API），别给它「一键出图」的说法 ——
正确做法是拿它的标签版去 midjourney.com/imagine 粘贴。

用户没提模型时用通用正文，**不要替他挑一个**：
默认模型是 `gpt-image-2`，而它要 API key。

### 4. 真的出图（Codex 里也能出）

```bash
node scripts/forge.js render --style ST-001 --theme TH-020 --out ./out
node scripts/forge.js render --draw 4 --out ./out        # 抽 4 组连着出图
node scripts/forge.js draw --n 3 --render --out ./out    # 同上，写法更短
```

命令**把图存成本地文件并打印路径**。要拿给用户看的只有路径，
不要把图片内容读进对话（base64 会污染上下文，而用户要看的是文件）。

| 参数 | 说明 |
|---|---|
| `--out 目录` | 存到哪，默认 `./forge-out/` |
| `--model` | 默认 `gpt-image-2`，**但它要 API key**；不想配 key 就用 `--model sana` |
| `--key` | 也可读环境变量 `POLLINATIONS_KEY`。只随请求头发送，不进 URL、不落盘 |
| `--ratio` | `1:1` / `9:16` / `16:9` / `3:4` / `4:3`，或 `1024x1536` |
| `--seed` | 复现同一张构图 |
| `--tries` | 默认 3。免 key 通道约一半请求被限流挡掉，重试是必需的 |
| `--wait` | 重试间隔秒数，默认 10 |

**`--model` 同时决定两件事**：走哪条通道，以及提示词按谁的语法写。
不要只把它当「选通道」—— 给 Flux 发一串 MJ 标签，
命令会正常退出、图也出得来，只是那张图不对。

文件名是 `模型__组合串`（`sana__ST-001+TH-020.png`）：
带模型名是因为同一组四步换模型出的是两张完全不同的图，
只看组合串分不出是哪一版的。

**出图前必须告诉用户的三条**（照抄，别省）：

1. 提示词会**离开本机**发到第三方服务器；
2. 出的图**带通道水印**，商用前要自己裁；
3. 图里的文字仍然是乱码，版式预留的空白区留给后期排字。

拿不到图时（连试 `--tries` 次都是 402）说清是配额问题，隔几分钟再来，
不要把「一张都没出」说成「生成失败」—— 两者的下一步动作不一样。

### 5. 五个调通的预设

```bash
node scripts/forge.js presets
```

小红书观点卡 / 电影分镜 / 电商主图 / 角色设定页 / 活动海报。
命令行可以直接交给用户，让他说「要第 2 个」或「改一下配色」。
预设比 `draw` 更适合「要有用的成品」，`draw` 更适合「想看点没见过的」。

### 6. 只报缺什么

```bash
node scripts/forge.js diagnose --style ST-001
```

## 在 Codex 里用：与网页端的差别

同一套库有两个入口 —— 网页和这个命令行。
网页版**不在技能包里**：在线地址 <https://gaoren7716-lab.github.io/anime-prompt-library/>，
或克隆整个仓库后打开根目录的 `index.html`。
在 Codex 里只有命令行，所以下面这些是**必须换做法**的地方：

**一、长文本不要读进对话。** 四步齐备的正文有 1500–2500 字符，
一次抽 6 组就是一两万字。要正文就一次取一组（`draw --n 1 --prompt`），
或者加 `--json` 之后只取需要的字段，不要 `draw --n 6 --prompt` 铺满屏幕。
出图之后也只给**文件路径**，不要把图读进上下文。

**二、判断「该问还是该抽」。** 网页端的用户在页面上自己看着办；
Codex 里你是那个要决定的人。规则见第 0 节：
说得出要什么就问四步，说不出就 `draw`。**不要连续追问三轮以上**——
第三轮还在问「你更喜欢哪种上色」的时候，`draw --n 4` 早就给出答案了。

**三、结构化输出优先 `--json`。** `build --json` / `draw --json` / `render --json`
的字段是固定的（组合明细在 `rows`、中英正文在 `prompt` / `promptZh`、
授权档在 `rights`、图路径在 `file`）。要二次处理就取字段，
不要去正则抠文本输出。

**四、出图前把三条边界说出去。** 见第 4 节，不要省。

**五、抽卡与出图都不写回任何状态。** `draw` 不改你或用户的任何设置，
`render` 只往磁盘写文件。所以可以放心连着调，
不会出现「抽了一次，之前选的四步被换掉了」这种事。

## 三条硬规则

**一、缺步必须说，不要静默补。**
脚本会给 `⚠ 缺步提示`，把每条的 `why` 念给用户。
不许把一段缺了版式的提示词说成"可以直接用了"。

**二、退出码 2 = 授权不能直接过。**
组合里含 R2/R3 时脚本以退出码 2 结束，并打印处理办法。
**这时不要把提示词当作可商用产物交给用户**，先读 `references/RIGHTS.md`，
按里面说的处理完再给。退出码 0 才代表可以直接用。

**三、正文里不写作品名和创作者名。**
本库的提示词正文只写可观察的视觉特征。
即使你从条目名称里看到了某部作品或某位创作者，
**也不要把它写进提示词正文**——那会把 R0 的正文变成 R3 的风险。
名称与徽章可以口头提，正文不能。

**四、用户说了模型，就按那个模型改写提示词。**
五个模型的语法不同（见第 3.5 节的表）。用 `--model`，
不要把通用正文发给所有模型 —— 那是「能出图」与「出对的图」的区别，
而错的图看起来只是「构图怪」，没人会去查提示词。
反过来，用户没提模型时**不要替他挑**，默认 `gpt-image-2` 要 key。

## 提示词该有多长

不是越长越好。本库的正文形态是「场景 → 技法执行 → 色彩 → 构图 → 排除项」，
单条 400–700 字符。合成后 1500–2500 字符属正常。

各模型该拿哪一版（**与第 3.5 节的表配套**，那里是脚本实际写法的依据）：

- **GPT-Image 2 / Nano Banana 2.1**：给完整正文，模型对长句与指令句的遵守度高。
- **Midjourney**：只给标签 + `--ar/--niji/--stylize`，正文太长反而糊。
- **Flux**：给完整正文（描述性散文），但**不要**加权重语法与质量词。
- **Sana**：给**短一档**的正文（题材 + 配色 + 画幅），
  它会把过长的后半段当补充说明而弱化主体。
- **SDXL / Illustrious / NovelAI**：用 `tags` + `negatives` 字段。

不要把英文正文和标签版拼在一起发——同一套约束写两遍，
模型会把它理解成两个独立要求，结果是权重混乱。

**MJ 的标签里不要混进参数。** 脚本分两个字段给就是为了这一点；
手工拼的时候保持「标签段 + 空格 + `--参数`」的顺序，
参数放中间会让整段降级成无效输入。

## 画幅不是一个可选项

版式条目自带 `ratio`（`3:4` / `1:1` / `9:16` / `16:9` 等），
脚本已经把它写进正文末尾。**用户拿去出图时要真的按这个比例设参数**，
否则出的是另一张构图。告诉用户具体比例。

## 目录结构

```
anime-prompt-forge/
├── SKILL.md
├── INSTALL.md
├── references/
│   ├── CATALOG.md        条目分类速查
│   ├── RIGHTS.md         授权四档与处理办法
│   ├── MODELS.md         模型适配
│   └── data.json         随包数据（独立安装时用，仓库内开发不需要）
└── scripts/
    ├── forge.js          全部功能，一个脚本
    ├── render-core.js    出图通道（assets/render.js 的逐字副本）
    ├── gacha-core.js     抽卡引擎（assets/gacha.js 的逐字副本）
    ├── model-prompts-core.js  按模型改写提示词（assets/model-prompts.js 的逐字副本）
    ├── build_catalog.js  生成 CATALOG.md
    └── build_bundle.js   生成 data.json + 同步上面三个副本
```

> 三个 `-core.js` 都是仓库里 `assets/` 的逐字副本，
> 由 `build_bundle.js` 同步（复制完立刻回读比对）。
> **改逻辑要改 `assets/` 那份**，改副本会在下次同步时被覆盖掉。

`scripts/forge.js` 会自动找数据源：仓库内跑（`<repo>/assets/`）用真实引擎，
独立安装则读 `references/data.json` + 两个 `*-core.js` 副本。两种布局产出**逐字相同**的结果。

那两个 `*-core.js` 是 `build_bundle.js` 复制过来的，**不要手改** ——
改了下次同步就被覆盖，而且 `tools/check_skill.js`【11】会当场报出分叉。
出图与抽卡的逻辑只有一个真源：仓库的 `assets/render.js` 与 `assets/gacha.js`。
